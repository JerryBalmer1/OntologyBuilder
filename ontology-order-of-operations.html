Order of operations

Ontology Builder — the pipeline definition. Companion to ontology-layering-model.html. That page says what the model is; this page says the sequence in which it gets built, per company, per run, every time. Human-readable here; machine-readable in the JSON block at the end of the file — and, because the vocabulary is the one CI systems already use, emittable as a pipeline YAML without translation.

How to read this document

Same conventions as the layering page. Every named container has one colour, used wherever that container is mentioned. Every container is bottom-up: the first item sits at the bottom and later items rest on it. The three pipelines read left to right, and each one contains or produces the next. Names are industry-standard, never invented: someone who has built a CI pipeline before should recognise every word here on sight.

Kinds — the page has two halves, and both are standard

The sequence half uses the vocabulary of a pipeline definition (Azure DevOps, GitHub Actions, GitLab — same words everywhere). The declarative half uses the vocabulary that sits beside a pipeline definition rather than inside it. Neither half is weaker; they are different kinds, and a reader who knows one already knows the other.

The three pipelines

Three pipelines at three cadences, read left to right. Onboarding runs once per company and invokes Build as its second stage. Build runs on every trigger and its published output is the ground stage of Operations, which is structural and runs once per estate. Every step sits inside a stage; every parallel sibling inside a stage is a job.

The fallthrough job

How one type id gets its layer. Cheapest, most certain path first; the tier recorded on the node is simply which rung caught it. This is the single job inside the classify stage, and what curation feeds.

Gates conditions & approvalsWhat every ▲ on this page has in common.
  • A condition is a predicate over an artifact, not a feeling. "types.json has N rows and all ids are unique" is a condition; "looks fine" is not.
  • An approval is a condition a human satisfies. There is exactly one on this page: curation. Everything else is checked by the build.
  • A failed gate stops. The agent reports which gate and which artifact, and does not proceed.
  • Conditions are checked by Invoke-Build, not by reading out/ manually. The agent never reads out/.
  • Gates never mutate. Checking a gate is knowledge work; it touches nothing live.
  • A gate that keeps failing for a good reason gets a written exception in config, not a bypass in code.
  • The gate between sources and transform is special: it is the contract every source type's adapter implements. Adding a source type means declaring it in config and satisfying that gate; nothing above sources changes.

Policies and artifacts

Policies constraintsTrue before, during and after every pipeline on this page.
  • Type ids, once minted, never change. Namespaced by provider. Renaming is a breaking change to the registry.
  • Layer names never change. Only the type-id mappings inside them grow. That is what makes layers.yaml portable between companies.
  • Classification is a property bag on the node, tiered. Nothing reads layer or role as a fixed field by name.
  • Hierarchy is an edge. contained_by alongside references; owned_by and depends_on slot in later without a refactor.
  • Existence tier is separate from label tier. Schema-mandated is certain; monitoring-implied is inferred.
  • Every source type returns the same shape. Nothing above sources knows which ones ran.
  • Every step lives in exactly one stage. A step with no stage is a design error, not a shortcut.
  • Source types are node types. source_type.* ids live in the same ontology as the resources they produce; the pipeline reads its own vocabulary from the graph.
  • Knowledge before engagement. Nothing below discovery touches a live system; discovery itself is read-only.
  • PowerShell 7.4+, one script per source, StrictMode Latest, System.Text.Json. Whole files, same filename.
